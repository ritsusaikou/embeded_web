## 约束先行

选型不该从「我会什么框架」开始，而应该从**约束**开始。这个项目的硬约束只有三条：

1. 目标机内存 512MB，且不是独占——内核、rootfs、必要守护进程都要占。
2. 单核 Cortex-A7，主频 528–792MHz，没有乱序执行、没有大缓存。
3. 存储是 SD 卡 / eMMC，随机写寿命有限，不适合高频日志。

这三条直接决定了：**任何常驻的、带运行时（runtime）的进程都是奢侈品。**

## 先算内存账

一个跑在板子上的网站，除了内容本身，还要付出「运行它」的固定开销：

| 方案 | 板上常驻内存 | 说明 |
| --- | --- | --- |
| Node SSR（Astro `output: 'server'`） | 60–120 MB | V8 堆 + SSR 运行时，冷启动要解析模板 |
| Next.js / Nuxt SSR | 150 MB+ | 框架层更厚 |
| Python Flask + gunicorn | 40–80 MB | 每个 worker 20MB 起 |
| PHP-FPM + Nginx | 30–60 MB | 每个 FPM worker 独立进程 |
| Go 单二进制 | 10–20 MB | 静态编译，协程轻，但需要交叉编译调试 |
| **Nginx 提供静态文件** | **3–8 MB** | 单 worker，`sendfile` 在内核态零拷贝发送 |

512MB 的机器上，Node SSR 会吃掉近五分之一内存，换来的是什么？**这个站点没有任何需要服务端计算的东西**——没有用户系统、没有数据库、没有实时接口。用 SSR 纯属为一个不存在的问题付出代价。

## 静态优先的三条收益

1. **内存**：只留一个 Nginx worker，3MB 级别。
2. **CPU**：请求路径上没有模板渲染、没有 JIT，全部是 `read()` + `sendfile()`，单核也能扛住几百并发。
3. **抗故障**：没有后端进程，就没有「后端崩了」这种故障模式。Nginx 挂了重启一次 50ms。

代价也很明确：**内容更新必须重新构建、重新上传**。对本项目（课程项目，每周更新几篇实验日志）来说，这个代价可以忽略。

## 那为什么构建工具还选 Astro

因为「运行时不要 Node」不等于「开发时不要工具链」。Astro 正好把这两件事分离得很干净：

- 开发时：`.astro` 组件、Markdown、布局复用、类型检查，写起来和现代框架一样舒服。
- 构建时：在 PC 上一次性渲染成纯 HTML + CSS。
- 运行时：产物就是一堆文件，**完全不需要 Node**。

这是 Astro 相比 Nuxt / Next 最关键的差异——后两者的默认心智模型是「要有一个 Node 服务在跑」，而 Astro 的默认输出是静态文件。

> 判断标准很简单：**如果页面在构建时就能确定内容，它就不该在运行时被渲染。** 博客、文档、项目展示页全都属于这一类。

## 如果将来必须动态

不是永远不需要动态。如果后面要加「板子实时状态」，也不必拆掉静态架构，有三条递增成本的路径：

1. **定时生成 JSON**：用 systemd timer 每 10 秒把 `/proc` 里的数据写成 `status.json`，前端 fetch。零常驻进程。
2. **CGI**：`nginx + fcgiwrap` 调一个 shell 脚本，开销 < 1MB。对本项目足够。
3. **Go 单二进制**：真要写接口时首选，交叉编译一条命令，常驻 10–20MB。

## 结论

**静态文件 + Nginx，不是妥协，而是这个约束下唯一的正解。** 全站 HTML+CSS 压缩后不到 40KB，Nginx 常驻 3.2MB，这套数字本身就是项目的一部分成果——后面在「性能实测」里会给出对比数据。
